# Oriz lead capture — design specification

## Purpose

Create a dedicated contact page that captures a prospective client's details before redirecting them to the appropriate Oriz WhatsApp number. The captured record must remain available in Supabase even when the visitor opens WhatsApp but does not send the prepared message.

## Scope

The first version includes:

- a responsive `/contato/` page consistent with the current Oriz visual system;
- required name, WhatsApp, and one-or-more service selections;
- secure server-side capture in Supabase;
- automatic assignment to Eudes, Wallyson, or both;
- a prepared WhatsApp message containing only the lead's name and selected services;
- editable lead status in the Supabase Table Editor;
- replacement of the site's main contact CTAs with links to the new page.

This version does not include authentication, an administrative interface inside the Oriz site, automatic notifications, a CRM pipeline, or automatic follow-up messages.

## Contact-page experience

The form is the primary content in the first viewport. It uses the existing off-white, black, and Oriz orange palette, editorial typography, generous spacing, and restrained motion.

Fields:

1. `Nome` — required text input.
2. `WhatsApp` — required telephone input with Brazilian-friendly formatting while preserving a normalized value for storage.
3. `Serviços desejados` — required multi-select controls using the six service names above.
4. An invisible honeypot field for basic automated-submission filtering.

The form includes a short privacy notice explaining that the information will be used by Oriz to respond to the request. It does not claim that submitting the form sends a WhatsApp message.

Submission states:

- Default: the primary action is available when required data is valid.
- Saving: the action becomes disabled and reads `Salvando contato…` to prevent duplicate submissions.
- Success: after Supabase confirms the record, the page redirects to the assigned WhatsApp conversation.
- Failure: the page preserves every entered value, shows a concise error, and offers another attempt. It does not redirect before a successful capture.

The prepared WhatsApp message is:

> Olá, sou {nome}. Tenho interesse em {lista de serviços} e cheguei pelo site da Oriz.

The lead's telephone number is stored in Supabase but is not repeated in the prepared message because WhatsApp already identifies the sender.

## Data model

Create a `public.leads` table with:

| Column | Type | Rules |
| --- | --- | --- |
| `id` | `uuid` | Primary key; generated by the database |
| `name` | `text` | Required |
| `whatsapp` | `text` | Required; normalized digits with optional leading country code |
| `services` | `text[]` | Required; one or more allowed service identifiers |
| `responsible` | `text` | Required; constrained to `Eudes`, `Wallyson`, or `Ambos` |
| `status` | `text` | Required; defaults to `Novo` |
| `source_url` | `text` | Page URL that led to the form, when available |
| `created_at` | `timestamptz` | Required; defaults to the database timestamp |

Allowed status values:

- `Novo`
- `Em atendimento`
- `Atendido`
- `Não convertido`

Status is edited manually in Supabase's Table Editor. No public website control may update a lead after insertion.

## Secure capture architecture

The public page sends a JSON request to a Supabase Edge Function. It does not insert into the table directly.

The Edge Function:

1. accepts only the expected request method and content type;
2. applies a strict origin allowlist for the production site and explicit local development origins;
3. rejects non-empty honeypot submissions;
4. normalizes and validates the name, WhatsApp number, services, and source URL;
5. calculates the responsible person from the service ownership rules;
6. inserts the lead using a server-side secret unavailable to the browser;
7. returns the approved WhatsApp destination and prepared message only after the insert succeeds.

The table has Row Level Security enabled and no public `SELECT`, `UPDATE`, or `DELETE` policies. Because the visitor is not signed in, the capture function accepts unauthenticated requests and performs its own validation before inserting. The browser receives only the Supabase project URL and publishable key used to invoke that function; it never receives a secret or `service_role` key.

The honeypot and strict validation provide basic abuse reduction without adding visible CAPTCHA friction. A managed CAPTCHA and stronger rate limiting are intentionally left for a later version if real traffic shows that they are necessary.

## Site integration

- Add the new page and its dedicated stylesheet and script, reusing existing shared navigation/footer assets where practical.
- Update the home-page contact button and menu contact link to `/contato/`.
- Update generated service and city CTAs through the page template, then regenerate all derived pages.
- Update directory, footer, and Insights contact links where they currently point to the old home-page contact section.
- Add the contact page to the sitemap and automated site verification.
- Keep the existing home contact section as an editorial CTA that links to the new form rather than embedding a second form.

## Validation and verification

Automated checks must prove:

- one or more services are required;
- unsupported service identifiers are rejected;
- Eudes-only selections route to Eudes;
- Wallyson-only selections route to Wallyson;
- mixed selections are stored as `Ambos` and route to Wallyson;
- the WhatsApp message contains the name and services but not the submitted telephone number;
- a failed database insert does not return a successful redirect target;
- the table has RLS enabled and the intended constraints;
- every main contact CTA resolves to the new contact page;
- the generated static pages and sitemap remain valid.

Browser verification covers desktop and mobile layouts, keyboard operation, validation messaging, saving/error states, absence of horizontal overflow, and the prepared WhatsApp URL without completing or sending a WhatsApp message.

## Deployment

The database schema and Edge Function are deployed to the user's existing Supabase project. The static contact page is committed to the current website repository and published through the existing `hostinger` branch workflow. Environment-specific Supabase values are kept out of committed secret-bearing files.
